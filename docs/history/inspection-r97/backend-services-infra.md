**يظهر في Render logs (مرة واحدة عند كل boot):**

### A.3 خلاصة Deliverable A

الانقسام مؤكد حرفيًا في الكود: نفس غياب `REDIS_URL` يُقابَل بسياسيتين متعاكستين على بعد 3 أسطر من بعضهما في تسلسل الإقلاع:

- **Migrations = fail-open** (`boot-migrations.ts:287-291`: لا Redis → "No coordination needed: just run") → الـ app يقلع ويخدم الـ traffic → لا deploy alert.
- **Schedulers = fail-closed** (`scheduler-coordinator.ts:43-53` تعليق F2: "a null client means NO leadership… fail-closed") + آلية الـ self-healing (حلقة الـ retry التي تستدعي `getRedisClient()`) **عاجزة هيكليًا** عن الإصلاح عندما يكون `REDIS_URL` نفسه مفقودًا، لأنها مصممة لالتقاط client يعيد الاتصال — ولا client موجود أصلًا.

## Deliverable C — مدخلات خطة الاستعادة

### C.1 ما يقوله `render.yaml` مقابل ما هو موجود فعليًا على Render

- `render.yaml:246-250`: `REDIS_URL` للـ web service يأتي من `fromService: type: redis, name: subnation-redis, property: connectionString`.
- `render.yaml:252-256`: الخدمة معرَّفة في الـ blueprint: `type: redis, name: subnation-redis, plan: free, ipAllowList: [], maxmemoryPolicy: allkeys-lru`.
- **قائمة خدمات Render الفعلية (سياق المهمة):** openwa-gateway, SmartBot, POS, Smart-Menu, zu-connect, lyosint, SubNation2 — **لا توجد خدمة redis**. إذن خدمة `subnation-redis` **غير مُنشأة على الإطلاق** (الـ blueprint لم يُطبَّق على هذا الجزء أبدًا، أو حُذفت) — وبالتالي `fromService` لا يولّد قيمة، و`REDIS_URL` يصل العملية فارغًا/غائبًا، فيتحقق المسار الموصوف في Deliverable A.
- `plan: free`: خطة Redis المجانية على Render قد لا تكون متاحة للـ org الجديدة — يجب التحقق من الـ dashboard قبل افتراض أن "apply blueprint" سيكفي.

### C.2 هل يستطيع الـ app تشغيل الـ schedulers بدون Redis إطلاقًا؟ — **لا**

الأدلة من الكود:

1. `scheduler-coordinator.ts:43-53` (تعليق F2): مسار الـ dev fallback القديم (leadership بدون guard) **أُزيل عمدًا في round-94** — "Now a null client means NO leadership (jobs stop safely, fail-closed)".
2. آلية الـ self-healing الوحيدة هي حلقة الـ retry التي تستدعي `getRedisClient()` (scheduler-coordinator.ts:138, 250) — وهي تعمل فقط عندما يكون `REDIS_URL` **مضبوطًا** وفشل الاتصال (الـ client object يبقى حيًا ويعيد الاتصال، redis-client.ts:254-265). مع env **مفقود** لا يوجد object أصلًا (redis-client.ts:180-203) → الحلقة تدور على `null` إلى الأبد.
3. الباقي داخل الـ scheduler stack لا يحتاج Redis فعلًا: الـ heartbeat له null-skip جاهز (`web-scheduler.ts:159-171`)، والـ alerting dedupe/rate-limit فاشلان fail-open، والـ migration lock عنده مسار `no_redis` — **الـ leader lock هو الاعتماد الصلب الوحيد على Redis في الطبقة كلها**.

### C.3 خيارات الاستعادة (مرتبة)

**الخيار 1 — استعادة Redis على Render (الأسرع، بدون كود):**

- إنشاء Key Value (Redis) service باسم `subnation-redis` من الـ dashboard (أي خطة متاحة؛ تجنّب افتراض free)، ثم ضبط `REDIS_URL` يدويًا على خدمة SubNation2 بقيمة الـ internal connection string، ثم redeploy. المسار اليدوي أضمن من "apply blueprint".
- ⚠️ **تحذير من تطبيق الـ blueprint كاملًا:** `render.yaml:258-297` يعرف أيضًا خدمة `subnation-worker` (dormant by design) — تطبيق الـ blueprint سيُنشئها فورًا، وهي تشغّل الـ schedulers **بدون leader lock** بينما الـ web ما زال `DISABLE_WEB_SCHEDULERS=false` → نافذة double-run موثقة في `render.yaml:278-286` نفسه. تجنَّب هذا المسار إلا مع إتمام خطوة flip في نفس نافذة الصيانة.
- بعد الاستعادة: أول boot سيأخذ الـ lock مباشرة (لا منافس)، وتعود كل الوظائف تلقائيًا. **الإغلاق الزمني منذ 09-08 لن يعالج نفسه** — راجع Deliverable D لما يجب تشغيله يدويًا/one-shot.

**الخيار 2 — تعديل كود minimal (تصميم فقط — لم يُنفَّذ التزامًا بـ ZERO modifications):**

- **التصميم A (الأصغر، env-gated):** داخل `acquireSchedulerLeadership()` — عند `!process.env.REDIS_URL && process.env.SCHEDULER_ALLOW_NO_REDIS === "true"`: منح الـ leadership فورًا (`isLeader=true`) بدون refresher/retry (لا يوجد منافس داخل العملية الواحدة)، مع `logger.warn` صريح + `noteRedisDegradedMode("single_instance_leadership")` + scheduler-state reason جديد `"single_instance_no_redis"`. المخاطر: انقسام دماغي لو scale-out أو لو أُنشئ الـ worker لاحقًا — يحتاج ضبط `DISABLE_WEB_SCHEDULERS` كضبط تشغيلي صارم (نفس انضباط render.yaml:223-236 الحالي).

- **التصميم B (الأمتن، مُوصى به): PG-advisory-lease backend** — استبدال خلفية القفل فقط مع إبقاء كل معمارية TTL/refresher/demote/retry الحالية:
  - جدول `scheduler_leader_lease` (id=1 singleton, `holder` text, `expires_at` timestamptz) — أو `pg_try_advisory_lock(<key ثابت>)` على connection مخصص من الـ pool.
  - `attemptAcquisition()` = `INSERT … ON CONFLICT (id) DO UPDATE SET holder=$instanceId, expires_at=now()+60s WHERE scheduler_leader_lease.expires_at < now() RETURNING holder` — إرجاع `instanceId` = "acquired"، لا صف = "busy".
  - الـ refresher (كل 20s) = `UPDATE … SET expires_at=now()+60s WHERE holder=$instanceId` — rowsAffected=0 → `demote()` الحالي كما هو.
  - `release()` = `DELETE … WHERE holder=$instanceId`.
  - ميزة: Postgres هو بالفعل اعتماد الـ money-path الموجود في كل بيئة (حتى dev) — لا بنية تحتية جديدة، ولا انقسام سياسات fail بين بيئة وأخرى. الـ migration نفسه يُضاف لـ `migrate.ts` (idempotent كما هو تقليد الملف).
  - **التوصية النهائية:** الخيار 1 فورًا (استعادة الخدمة) + التصميم B كـ follow-up ليصبح الـ scheduler مستقلًا عن توفّر Redis نهائيًا (Redis يبقى لتحسين الـ perf/dedup فقط).

**لا يوجد mitigation صفري-كود مؤقت للـ schedulers** — تشغيل الـ retention يدويًا عبر scripts بعد كل deploy ليس حلًا مستدامًا.
