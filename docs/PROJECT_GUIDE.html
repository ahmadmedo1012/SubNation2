١ ما هو المشروع؟

الهوية، الفكرة، وطريقة عمل المتجر من منظور المستخدم — قبل الغوص في التفاصيل الهندسية.

الفكرة في سطر واحد

متجر إلكتروني عربي بالكامل (من اليمين لليسار) لبيع اشتراكات المنصات الرقمية في السوق الليبي — نتفليكس، سبوتيفاي، ChatGPT Plus، ExpressVPN، رخص Windows، أدوبي وغيرها (45 منتجًا حاليًا) — بأسعار بالدينار الليبي (LYD)، والدفع عبر محفظة داخلية تُشحن بتحويل مالي، والتسليم فوري ومشفّر بعد الشراء.

🗄️ Neon Postgres إلزامي

DATABASE_URLDB_POOL_MAXPG_STATEMENT_TIMEOUT_MS

عند غيابها: يفشل الإقلاع فورًا — لا قاعدة، لا نظام.

🔑 الأسرار الثلاثة إلزامية

يُتحقق منها عند الإقلاع ويُرفض البدء إن كانت ضعيفة أو ناقصة:

  • SESSION_SECRET — توقيع JWT للمستخدمين (≥32 حرفًا)
  • ADMIN_JWT_SECRET — توقيع JWT للمشرفين (≥32، ويجب أن يختلف عن السابق)
  • ENCRYPTION_KEY — مفتاح AES-256-GCM لبيانات الاعتماد (64 سداسيًا)

وفي الإنتاج: قائمة أصول CSRF غير فارغة (CSRF_ALLOWED_ORIGINS).

◆ البنية التحتية المُحيطة

المكوّن الدور
GitHub المستودع الرسمي (ahmadmedo1012/SubNation2) — فرع main فقط. كل دفعة تشغّل CI، وCoolify يبني ويحدث الإنتاج تلقائيًا (Webhook).

◆ 7.1 تسجيل الدخول (ثلاث طرق + المشرفون)

Google

تسجيل الدخول من المتصفح عبر Firebase → إرسال رمز ID إلى /auth/firebase/session → التحقق من الخادم بحساب الخدمة → إيجاد/إنشاء المستخدم + ربط الهوية → جلسة JWT (كوكي httpOnly لمدة 30 يومًا) مع سطر جلسة قابل للإبطال.

Telegram

ثلاث صور: Widget الكلاسيكي (تحقق HMAC)، Mini App (دخول تلقائي داخل التطبيق)، وOIDC حديث (Authorization Code + PKCE ضد oauth.telegram.org). بيانات البوت تُدار من لوحة الإدارة وليست متغيرات بيئة.

WhatsApp OTP

/auth/whatsapp/start يولّد رمزًا (صلاحية 5 دقائق، ≤5 محاولات، سقف إرسال شامل 500/يوم) ويرسله عبر بوابة OpenWA → /verify يفحص الرمز → جلسة. حمايات: قفل تدريجي (15→240 دقيقة) وحدود إرسال لكل هاتف/IP.

المشرفون

اسم مستخدم + كلمة مرور (argon2) + تحقق TOTP إلزامي إن كان مُسجَّلًا → جلسة 8 ساعات بسرّ مستقل + سطر admin_sessions. كل عملية إدارية تُسجَّل في audit_logs وتحمل نطاقًا من: all · orders · finance · inventory · support · users · admins · settings.

◆ 7.2 شحن المحفظة (Top-up)

١العميل يطلب شحنًاالمبلغ + طريقة الدفع (تحويل مصرفي أو LyPay) + الشبكة (ليبيانا/مدار/سداد/LyPay) — بحد أقصى 3 طلبات معلّقة.
←
٢فحوص الإنشاءتحقق من المبلغ والشبكة + منع تكرار دائم (مفتاح Idempotency) + فحص مخاطر التكرار (تحويل مشابه خلال 24 ساعة → إشارة «⚠ خطر تكرار محتمل» للمشرف — إشارة مراجعة وليست رفضًا).
←
٣بطاقة المشرفتصل بطاقة تيليجرام للمشرف (⏳ معلّق / ✅ / ❌) — الموافقة من تيليجرام نفسه أو من الموقع.
←
٤الموافقة الذرّيةمعاملة واحدة: إعادة فحص الحالة → إضافة الرصيد إلى السجل → مكافأة الإحالة إن كانت أول شحنة → مكافأة ترحيب (5.00 د.ل).
←
٥إشعار العميلإشعار + تحديث لحظي للمحفظة عبر Socket.IO.
لماذا هذا التصميم؟ الموافقة idempotent (لا يمكن إضافة الرصيد مرتين لنفس الطلب حتى لو ضُغط الزر مرتين)، والرصيد لا يُعدَّل مباشرة قط — فقط سطور سجل جديدة.

◆ 7.3 الشراء (Checkout) — قلب النظام المالي

١قبل المعاملةحظر المخاطر الصلب (423) → الحاجز الناعم → مفتاح Idempotency (إعادة تشغيل نفس الطلب تُعيد نفس النتيجة) → تسعير نهائي + فحص الرصيد.
←
٢المعاملة الذرّيةكل ما يلي ينجح أو يُلغى معًا — انظر الصندوق أدناه.
←
٣بعد الالتزام فقطالإشعارات، تحديث تيليجرام، إشارات المخاطر — لا شيء منها يظهر إن رُجعت المعاملة.
⟦ داخل المعاملة الواحدة — كلها أو لا شيء ⟧
  • حجز وحدة مخزون — كاتب واحد عبر FOR UPDATE SKIP LOCKED (لا يمكن لوحدتين أن تُحجزا مرتين مهما بلغ التزامن)
  • خصم الرصيد — تحقق + خصم متشائميان؛ أي تعارض → 409 قابل لإعادة المحاولة (النقود لم تتحرك)
  • استهلاك الكوبون (إن وُجد) وترحيل قيمته
  • منح نقاط الولاء — سطر جديد في points_ledger
  • إنشاء الطلب — بـ لقطة سعر مجمّدة (لا يتغير سعر طلب مكتمل أبدًا)
  • سطر سجل المحفظة — الخصم الموثّق
التسليم الفوري: بيانات الاعتماد كانت مشفّرة في جدول المخزون (AES-256-GCM)، وتُنقل إلى الطلب لحظة اكتماله — فيظهر للعميل فورًا في صفحة الطلب، ويفكّ الخادم التشفير للمالك فقط. أي فشل في فك التشفير = فشل مقفول (لا تسليم لبيانات فاسدة).

◆ 7.4 الاسترداد (Refund)

من لوحة الإدارة (نطاق orders) — معاملة واحدة: تغيير حالة الطلب إلى «مُسترد» + إعادة الرصيد بسطر سجل جديد + سحب نقاط الولاء الممنوحة + معالجة خانة الكوبون. الحالة الجماعية تعيد أغلفة 207 متعددة الحالات مع الحقيقة الأرضية لكل طلب (الطلبات الفاشلة لا تحرّك مالًا).

◆ 7.6 الولاء والإحالات

💎 النقاط

100 نقطة = 1.00 د.ل. تُمنح مع كل عملية شراء، وتُحوَّل إلى رصيد بحِزم كاملة فقط — التحويل idempotent دائم.

🏅 الطبقات

مشتقّة من إجمالي الإنفاق المؤهّل: فضية 500 · ذهبية 2,000 · بلاتينية 5,000 د.ل.

🤝 الإحالات

المُحال الجديد: مكافأة ترحيب 5.00 د.ل عند أول شحنة معتمدة. المُحيل: 50 نقطة عند أول شحنة معتمدة للمُحال.

←
٢صياغة المسوداتقوالب عربية لكل حقل (وصف قصير/طويل، مميزات…) → فحص جودة (نسبة عربية + حدود أطوال).
←
٣مراجعة المشرفطابور مسودات في اللوحة مع حالة تشخيص حقيقية (لماذا لا تعمل الميزة إن كانت معطّلة — بالترتيب الصحيح للأسباب).
←

◆ 7.8 محرك المخاطر

كل أحداث الدخول/الشراء/الشحن تُصدر إشارات (بعد الالتزام) → محرك التقييم يجمع قواعد قابلة للتعديل من اللوحة (بـ DSL خاص) + إعدادات مُخزَّنة ككاش + صيغة ثقة واتجاه لكل مستخدم → النتيجة واحدة من ثلاث:

  • لا إجراء — الوضع الطبيعي.
  • حاجز ناعم — احتكاك على مسارات المال: إعادة مصادقة إجبارية أو حاجز مؤقت قابل للفك.
  • حظر صلب — رفض 423 مقفول على مسار الشراء (معطَّل افتراضيًا؛ يُفعَّل من إعدادات المخاطر فقط).

فلسفة الأمان: أي خطأ داخلي في المحرك يسمح للطلب بالمرور (fail-open على الأداء، والحماية الفعلية في مسارات المال نفسها). لوحة المخاطر (نطاق users) تعرض الأحداث والوسوم والقواعد والإعدادات.

◆ 7.9 قوانين المال السبعة عشر (M1–M17)

المستودع يفرض 17 قانونًا ماليًا موثّقة في docs/FINAL_MONEY_INVARIANTS.md ومُثبَّتة باختبارات. خلاصتها:

  • الموافقة على الشحن والمشروع (الشراء) والاسترداد: معاملات ذرّية واحدة — لا حالة وسيوية تُلمس المال.
  • منع التكرار الدائم على كل مسار مالي (نفس المفتاح = نفس النتيجة؛ أي تعارض = 409 مصنَّف).
  • الرصيد السالب مستحيل — بوابات داخل المعاملة.
  • سعر الطلب مجمّد — لا يوجد أي مسار يعدّل مبلغ طلب.
  • المخزون كاتب واحد — وحدة تُحجز مرة واحدة مهما بلغ التزامن.
  • الأحداث بعد الالتزام فقط — لا إشعار كاذب ينجو من تراجع معاملة.
  • عرض الدينار بصيغة واحدة في كل الواجهة: 1,234.56 د.ل (بلا -0 وبلا قيم غير منتهية).

١١ النشر والتشغيل

سلسلة النشر، بوابات CI، النسخ الاحتياطي، والمراقبة — كما تعمل فعليًا اليوم.

◆ سلسلة النشر (Push-to-Deploy)

١git push إلى mainدفعة conventional commit واحدة — لا دفع قسري أبدًا.
←
٢GitHub Actionsكل بوابات الجودة على الشجرة الحقيقية (انظر الجدول أدناه).
←
٣Webhook → Coolifyبناء صورة Docker من المستودع مباشرة.
←
٤تحديث متدرّج مقيَّد بالصحةلا يدخل الجديد إلا بعد نجاح /api/healthz — الدورة الكاملة ~12–15 دقيقة.

◆ بوابات CI (على كل دفعة كود)

البوابة ما تمنعه
مسح الأسرار (gitleaks — كل التاريخ) أي سرّ يُرتكب في أي لحظة
lint + typecheck (×4 حزم) أي انحراف أسلوب/أنواع
توازن OpenAPI ↔ المسارات مسار بلا توثيق أو توثيق بلا مسار
تزامن رموز الأخطاء + معاملات الرؤوس رموز غير معرَّفة أو رؤوس تضيع
انجراف Drizzle اختلاف المخطط عن سلسلة الهجرات
اختبارات الوحدات ×3 (خلفي/أمامي/سكربتات) أي كسر سلوكي — 5,465 اختبارًا
بناء الإنتاج + ميزانية الحجم انفجار حجم الحزمة الأولية
تدقيق CVE على اعتماديات الإنتاج ثغرة حرجة في مكتبة إنتاج
بوابة نمط واجهة impeccable أنماط UI معادية للجودة

اختبارات E2E تُطلق بالجدولة والطلب اليدوي فقط (ليست على كل دفعة)؛ دفعات التوثيق فقط تتخطى البوابات الثقيلة عبر مرشح المسارات.

◆ النسخ الاحتياطي والتعافي

💾 نسخ ليلي

استعادة لنقطة زمنية على خطة Neon الحالية (~6 ساعات نافذة) — النسخة الليلية هي مسار التعافي الأساسي.

◆ المراقبة والتنبيه اليومي

🩺 الصحة

/api/healthz (عام، هو فحص Coolify) · /healthz/live و/summary عامة · /healthz/ready والفحوص العميقة للمشرفين (settings) · صفحة /status العامة للمستخدمين.

📈 المقاييس

Prometheus على /api/metrics (محمي برمز) — طلبات HTTP، نتائج المصادقة، المقابس، Web Vitals من العملاء (منارة /api/cwv).

🚨 التنبيه

Sentry (خطأ/أداء/إعادة تشغيل) + قناة تيليجرام للعمليات + مراقب خارجي كل 5 دقائق (توفر + شهادة TLS + المنافذ).

📕 دليل العمليات

OPERATIONS_RUNBOOK.md في جذر المستودع — نقطة الدخول الرسمية للمناوبات: فرز التنبيهات قاعدة-قاعدة، لوحات القيادة، الاسترجاع.
