## Findings

### L8-1 · P3 · `createUserSession` swallows session-row insert failures and mints a BORN-DEAD session — stale "audit/telemetry" comment describes a posture that no longer exists
- **Evidence:** `backend/src/lib/session.ts:30-57` — "The DB insert is best-effort: an audit/telemetry row must never block a successful login. On insert failure we still return a valid token (the sessionId is embedded either way)" + `logger.warn(…, "[session] row insert failed (non-fatal — token still issued)")`. But since H1 (2026-09-06)/93-A1 the row IS the session: `middlewares/requireUser.ts:58-79` rejects any sid-bearing token whose row is missing (`isSessionRowLive` → false → 401 SESSION_EXPIRED), and `routes/auth.ts:452-463` (/api/auth/probe) answers `authenticated:false` for the same reason. So an insert failure produces a 200/201 mint + `Set-Cookie` for a session that dies on the very next request: the SPA hydrates "logged in", the probe immediately says no, and the user bounces back to /login — a login loop for as long as the insert keeps failing, while the log calls it non-fatal.
- **Root cause:** the fail-open-at-mint posture predates the row becoming the revocation truth; the comment/log line were never revisited. Note the **asymmetry**: the admin twin `createAdminSession` (`lib/admin-session.ts:44-61`) does NOT swallow the insert error — a failure propagates and the login route answers an honest 500.
- **Proposed fix:** propagate the insert failure (or retry once) so the mint routes answer 500 — exactly the admin-side shape; at minimum rewrite the comment and raise the log to error level. One-line `throw` after a single retry is the smallest honest change.
- **Test requirement:** mock `db.insert(sessionsTable)` to reject → POST /api/auth/whatsapp/verify (or /firebase/session) must NOT answer 200/201 with a cookie for a session whose row was never written (assert 500, or the documented new behavior).
- **Risk:** low frequency (needs a targeted sessions-insert failure while selects work — statement timeout/pool contention), zero security impact (fails closed, confusingly); user-visible login loop + operator-misleading telemetry.

### L8-2 · P3 · The TOTP step-boundary race class is closed at only 2 of 5 mint sites — 3 sibling assertions in the same suites can still flake CI exactly like the incident 528ef39 fixed
- **Evidence:** success-expecting `generateSync` mints WITHOUT the regenerating-retry arm:
  - `routes/admin/__tests__/2fa-totp-encryption.test.ts:283` — legacy-plaintext verify-2fa, `expect(verify2fa.status).toBe(200)`;
  - `routes/admin/__tests__/2fa-totp-encryption.test.ts:334` — verify-setup inside the wrong-code test, `expect(verifySetup.status).toBe(200)`;
  - `routes/admin/__tests__/2fa-verify-setup-lockout.test.ts:189` — "…then the correct code completes the enrollment", `expect(ok.status).toBe(200)`.
  (The armored sites are `2fa-totp-encryption.test.ts:206/217` and `:241/247`; `2fa-verify-setup-lockout.test.ts:168` is race-immune because the lockout check 429s before code verification.)
- **Root cause:** the R142 hardening covered the flagship end-to-end flow's Steps 2 and 4 only; the same code-mint idiom at the other assertion sites was left bare. Pre-fix the file family had ~5 exposed sites; post-fix 3 remain — the residual CI flake probability is ~60% of the rate that produced the original incident.
- **Proposed fix:** extract the retry idiom into a helper (`postJsonExpecting2faOk`) or, better, make it deterministic: before minting, sleep until mid-window — `const ms = 15000 - (Date.now() % 30000); if (ms > 0) await sleep(ms)` — then mint; applies to all 5 sites and removes the class entirely.
- **Test requirement:** none new (this IS the test fix); pin with a comment referencing 528ef39.
- **Risk:** spurious CI red on a genuinely valid code (~RTT/30s per site per run) → erodes trust in the 2FA suites; no production impact.

### L8-3 · P4 · User-side session-liveness probe fails OPEN on DB error (admin side fails closed) with no Sentry capture — revocation is unenforceable for the outage window
- **Evidence:** `middlewares/requireUser.ts:80-90` — "DB probe failure: fail OPEN for the signature-valid token … logger.warn('[auth] session row probe failed — allowing on JWT strength')"; same posture at `routes/auth.ts:464-472` (probe). Contrast: `requireAdmin` has no try/catch around `isValidAdminSession` (`middlewares/requireAdmin.ts:102`) → a DB error propagates → 500 (fail closed).
- **Root cause:** documented availability trade-off (in-line: hard-failing every request during a Postgres blip would take the site down) — the finding is the (a) user/admin asymmetry and (b) observability: a `logger.warn` with no `captureSubsystemException`, so a prolonged fail-open window is invisible in Sentry.
- **Proposed fix:** keep the trade-off but add `captureSubsystemException("auth", err, { route: "requireUser.session-probe" })` (or a deduped capture) so extended windows are observable; optionally a consecutive-failure circuit breaker that flips to fail-closed after N misses.
- **Test requirement:** unit test pinning the fail-open verdict + (if added) the capture call.
- **Risk:** a stolen-then-revoked token gains free requests only while the sessions probe specifically throws while the rest of the request path works — narrow; consistent with the documented posture (H-5-class adjudication).

### L8-4 · P4 · Stale doc: admin cookie described as "7-day lifetime" while every actual TTL is 8 hours
- **Evidence:** `routes/admin/auth.ts:32-34` — "a tighter 7-day lifetime reflecting admin privilege" vs `ADMIN_SESSION_TTL_MS = 8 * 60 * 60 * 1000` (`lib/admin-session.ts:30`), `signAdminToken(…, { expiresIn: "8h" })` (`lib/admin-session.ts:56-59`), cookie `maxAge` 8 h (`routes/admin/auth.ts:43-47`). (Also: the literal `httpOnly/secure` keys at `:44-45` are dead — immediately overridden by the identical values in the spread from `getAuthCookieOptions`; harmless but confusing.)
- **Root cause:** comment drift across the A8-05 tightening.
- **Proposed fix:** one comment edit ("8-hour"); optionally drop the two dead literal keys.
- **Test requirement:** none (doc-only).
- **Risk:** an operator auditing session length from the comment mis-sizes the revocation window by 21×.

### L8-5 · P4 · Account-link commit and new-user identity upsert are non-transactional two-statement writes (E-6 class)
- **Evidence:** `services/firebase-auth.service.ts:417-439` — consented link = `updateUserIdentity(candidate.id, …)` then `upsertIdentity(updated.id, …)` with no `db.transaction`; `:459-503` — new-user INSERT is a tx but `upsertIdentity` runs after it, outside. A failure between the pair leaves `users.firebaseUid` set with no `user_auth_identities` row (or a created user with no identity row) → the 500 lands on an otherwise-successful link/signup.
- **Root cause:** same shape as R142 E-6 (support ticket writes) — sequential writes without rollback.
- **Proposed fix:** wrap each pair in `db.transaction` (both handlers hold all values locally). Recovery today is benign — the next login re-runs the resolver and upserts the identity — which is why this is P4.
- **Test requirement:** failure-injection between the two writes asserts no partial state (or documents the self-heal).
- **Risk:** transient 500 + inconsistent identity row until next login; no money, no auth bypass (the consent token itself is one-shot and correct — see below).

### L8-6 · P4 (info) · No server-side cap on concurrent live sessions per user
- **Evidence:** every mint inserts a fresh `sessions` row (`lib/session.ts:41-47`); revocation is per-row (`DELETE /api/auth/sessions/:id`, `routes/auth.ts:868-881`, ownership-scoped) or all-rows (logout-all, `:122`). Issuance is bounded only by the mint-route rate limits (`app.ts:230-270`: authLimiter 10/15min/IP on firebase session+refresh and telegram, whatsapp verify; whatsappStart 20/15min).
- **Adjudication:** passwordless marketplace, every mint requires passing a provider challenge (Google token / Telegram HMAC / delivered OTP); multi-device is the product behavior; `GET /sessions` display is clamped at 200 (E-5). No cap is a reasonable posture, recorded for completeness. If a "max N live sessions" policy is ever desired, it belongs in `createUserSession`.
