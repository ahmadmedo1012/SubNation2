# R146 audit — backend services, jobs, worker, money paths, db layer

Agent: 146-AUD-2 (ponytail-audit-backend-services) · Base: 4dca48c · READ-ONLY.

**What this part does:** The services layer owns every money mutation (checkout claim + charge, topup approval/credit, refund, admin adjustment), the OTP/auth orchestration (WhatsApp OTP, Telegram login, Firebase login), the OpenWA WhatsApp gateway client with its settle/warm-up gates, and the notification/alerting pipes. The jobs + worker layer runs the cron retention ladder, the boot one-shot catch-ups, and the (currently image-deleted) dedicated worker entry. The db layer (`shared/db`) is the Drizzle schema, the pg pool with statement timeouts, and the dedicated advisory-lock pool.

**Load assumed:** real public storefront (subnation.ly) with concurrent customers, money involved, and two long-lived processes (API server + background worker). Note: the live production shape today is ONE process (`SINGLE_INSTANCE_MODE=true`, all schedulers embedded, `dist/worker.mjs` deleted from the image — Dockerfile:272); the worker is the repo's own documented migration path, so I judged worker-path code against that documented topology too.

Method note: checkout/topup/refund/adjustment/idempotency/manual-provider/ledger have been hardened across many prior rounds (F-006, F10, B2-01..05, H5, R93-DATA, R115, R130…) and carry 49 service test files + 39 job test files. ## Should fix

### 1. Risk pipeline still has five unbounded Redis writes — the one module that escaped the repo-wide timeout rule
- **What this is:** `getRiskConfig()` (risk-config-cache.service.ts) caches the risk thresholds in Redis; `markPipelineDegraded()` (risk-scoring.service.ts:265) writes a degraded flag; `invalidateRiskConfig()` (risk-config-cache.service.ts:144-156) dels + publishes; `ensureInvalidationSubscription()` (risk-config-cache.service.ts:158-178) duplicates + connects a subscriber.
- **Problem:** The repo's R2/F3 rule ("every Redis op bounded by `withRedisCommandTimeout` — a ready-but-black-holed socket must never queue a command forever") is applied to the GET at risk-config-cache.service.ts:75 (its own comment says so), but the SET at line 121, the DEL/PUBLISH at lines 150-151, the `sub.connect()` at lines 165-166, and risk-scoring.service.ts:265's SET are all raw awaits. Concrete case: REDIS_URL is provisioned (the cache/alerting layers auto-activate when it is), the socket goes ready-but-black-holed (the exact outage class F3 documented), the in-memory config cache expires (60 s TTL) → the bounded GET times out → the DB read succeeds → line 121's unbounded SET queues forever → `getRiskConfig` never settles → every `scoreEvent` fire-and-forget promise (emitted from login/checkout paths) hangs and piles up with zero Sentry signal. The admin `PUT /api/admin/risk/config` hangs the same way on the unbounded del/publish. Dormant today (production runs REDIS_URL unset), live the moment Redis is turned on.
- **Fix:** Wrap all five sites in `withRedisCommandTimeout(...)` exactly like the GET at line 75 — one line each, no behavior change on the healthy path.
- **If we skip it:** The first Redis incident after provisioning Redis wedges the risk pipeline silently and hangs the admin risk-config save; the fix class is already proven everywhere else in the repo.

### 2. Concurrent exhaustion of a coupon's last slots never fires the "coupon maxed" operator signal
- **What this is:** After the atomic coupon increment, checkout decides whether to notify the operator (Telegram card + admin-alert drawer) that the coupon hit maxUses — checkout.service.ts:601-648, signal consumed at :906-913.
- **Problem:** The check at checkout.service.ts:641 uses `newUsedCount = appliedCoupon.usedCount + 1`, computed from the PRE-transaction read. Concrete case: maxUses=2, usedCount=0; buyers A and B redeem the last two slots concurrently. Both transactions serialize on the row lock, both guarded UPDATEs succeed (final usedCount=2), but each computed its own `newUsedCount = 0 + 1 = 1 < 2` — so neither fires `notifyCouponMaxedOut`/`logAdminAlert`. The coupon sits exhausted in the DB with no operator signal, and the next buyer gets a bare COUPON_EXHAUSTED 409 the operator was never warned about. Money is safe (the guarded UPDATE prevents over-redemption); the lost part is the operator-facing signal. The UPDATE at :635-639 already RETURNs the true post-increment row (`updatedCoupon.usedCount`) — it is simply ignored.
- **Fix:** Signal on `updatedCoupon.usedCount >= appliedCoupon.maxUses` instead of the stale computed value. One-line change. Add the concurrent-exhaustion case to `checkout-coupon-maxed-postcommit.test.ts` (it currently covers only the sequential single-buyer path).
- **If we skip it:** Coupons that drain fast (the whole point of a flash campaign) are the ones most likely to hit the concurrent window — exactly the coupons the operator most wants the exhausted alert for.

### 3. Telegram and Firebase first-login races surface as raw 500s — the class WhatsApp already fixed (F6)
- **What this is:** The find-or-create user steps for Telegram (telegram-auth-flow.ts:116-135) and Firebase (firebase-auth.service.ts:515-540) do a plain INSERT into `users` with no duplicate-key mapping.
- **Problem:** Concrete case: a double-tap on Google sign-in sends two concurrent `POST /api/auth/firebase/session` requests with the same idToken. Both pass verification, both find no existing user (step 1/3 miss), both INSERT — the loser trips the `users.phone` UNIQUE constraint (both compute the same `f_<sha(uid)>` placeholder) or `firebase_uid` UNIQUE as an unclassified 23505, which routes to the route's generic "non-Firebase error" branch (routes/auth.ts:~662) → 500 with a raw English Postgres message, for a registration that actually succeeded (the winner's request created the account). Retry works (step 1 then finds the row), but the user sees a scary 500 once. The same window exists for Telegram when two different initData payloads (two devices) race. WhatsApp closed this exact class in round-94 F6 (the OTP consume CAS makes the loser return a clean "consumed" 401); the two sibling channels never got the parity fix. Secondary effect: the Telegram replay-hash claim is taken BEFORE find-or-create (telegram-auth-flow.ts:245-248, 440), so when the insert throws, the hash stays claimed and the legitimate retry with the same payload gets "replay detected" until the TTL.
- **Fix:** Catch 23505 on the INSERT in both find-or-create paths, re-read by `telegram_id`/`firebase_uid`, and return the winner's row as a normal login. ~6 lines each, mirroring the F6 pattern.
- **If we skip it:** First-time sign-ins on the two provider buttons can 500 under double-submit — the most double-submitted moment in any storefront UI — while the third provider handles it cleanly.

### 4. Flipping to the dedicated-worker topology silently kills five of the alerting rules
- **What this is:** The alerting evaluator reads its signals from the local prom-client registry (`evalCounterDelta`: alerting.service.ts:430-449, `evalHttp5xxRate` :507-544, `evalHttpP95Latency` :563-623; absent metric → `return false`). worker.ts:135-137 starts the evaluator in the worker process ("so a horizontally-scaled web tier never produces duplicate alerts"), and boot-one-shots.ts/web-scheduler.ts document the dedicated worker as the migration path.
- **Problem:** Concrete case: the operator follows the documented path — `DISABLE_WEB_SCHEDULERS=true` on the web tier plus a dedicated worker process. The ONLY alerting evaluator now runs in the worker, whose prom-client registry never sees `http_requests_total`, `http_request_duration_seconds`, or `auth_outcomes_total` (those counters increment in the web process's memory only — prom-client registries are per-process). `getSingleMetric` returns undefined → `return false` → `api_5xx_rate_high`, `api_p95_latency_high`, `auth_failure_rate_high`, `abnormal_lockouts`, and `firebase_verifyidtoken_failures` never fire again, silently — no error, no metric, nothing in the runbook (FINAL_MONITORING.md describes only the current single-instance shape). Today's single-process production is unaffected (the evaluator rides the web leader where the counters live); this is a trap armed for the documented topology change.
- **Fix:** Smallest honest fix: keep rule evaluation where its signals live — do not start the alerting evaluator in worker.ts (or gate the five HTTP/auth rules to the web process and document the split with a `shortcut:` comment naming the limit). Moving the signals to Redis counters would be the full fix but is a bigger change than the problem needs today.
- **If we skip it:** The day the worker split happens, the store loses 5xx-rate, latency, and auth-failure alerting without any signal that it happened — the "alerting silence during a known incident" runbook row will point operators at the wrong causes.
