# R146 audit — frontend route/page layer (agent 146-AUD-3)

What this part does: `frontend/src/pages/` (30 storefront pages + 22 admin pages), `frontend/src/app/` (the wouter route tree, lazy page registry, boot head-start, chunk warm-up, query client) and the entry files (`App.tsx`, `main.tsx`, `instrument.ts`) are the SPA's route layer: they decide which page chunk loads, where every fetch happens, which skeleton/error/empty state a visitor sees, and how the money funnels (checkout, wallet/topup, cart, PDP buy, order receipts) talk to the API. Load assumed: a real public Libyan storefront (subnation.ly) with concurrent desktop AND mobile customers, mobile-majority, money involved.

Base read: checkout.tsx, wallet.tsx, product.tsx, orders.tsx, order-detail.tsx, cart.tsx, home.tsx, category.tsx, flash-sales.tsx, loyalty.tsx, referrals.tsx, notifications.tsx, profile.tsx, support.tsx, login.tsx, register.tsx, onboarding.tsx, auth-callback.tsx, telegram-callback.tsx, status.tsx, not-found.tsx, terms.tsx, all of src/app/*, App.tsx, main.tsx, instrument.ts, and admin/topups.tsx in full; the other admin pages were skimmed (query wiring + their test rosters). The R143/R144/R145 closed items were checked and are NOT re-reported here.

**Honest state of the old R143 "storefront duplicate fetch logic" item (L16-3/L16-5):** CLOSED. R144-C1/C2 threaded the whole storefront user-side family onto `customFetch` (20 sites) and `storefront-raw-fetch-gate-r144.test.ts` pins the floor: the only raw `fetch(` left in non-test sources is an 8-file allowlist (auth boot, healthz, beacon, admin-session wrapper, head-start, routes guard), none under `pages/`. I verified the cross-page cache contracts hold: `getListOrdersQueryKey()` = `["/api/orders"]` prefix-matches BOTH home's strip key and the orders page's `["/api/orders","load-more"]`, so checkout/product invalidations refresh both. The remaining manual `useQuery + customFetch` sites (loyalty, referrals, orders/notifications paging) are documented decisions (generated client can't express `?page=` yet; shared-key contract pinned). No duplicate-fetch defect found in the current state.

No Must-fix findings. Everything below is Should fix / Nice to have.

## Should fix

1. **Legacy numeric product URLs pay a double fetch and flip the live PDP back to a skeleton** (`frontend/src/pages/product.tsx:107-167`, esp. `:151-167` and `:590`)
   - **What this is:** `/product/:slug` accepts legacy numeric ids. The page fetches by id, renders the full PDP, then rewrites the URL to the slug form with `history.replaceState`.
   - **Problem:** wouter 3.9 monkey-patches `replaceState` into a location change (the repo's own `lib/navigation-quiet.ts:5-8` says so). So after the rewrite, `param` becomes the slug, `isLegacyNumeric` flips false, and `product`/`isLoading` switch to the `bySlugQuery` — whose key `["product-by-slug", slug]` has no data. Line 590 (`if (isLoading) return <RouteSkeleton …/>`) then replaces the PDP the visitor is already reading with a full-page skeleton until the by-slug request lands. Net effect for every legacy deep-link (bookmarks, pre-migration sitemap entries, old WhatsApp links): skeleton → content → **skeleton again** → content, plus the same product fetched twice (by-id response discarded). The R117 F-4 fix suppressed the scroll/focus yank of this same rewrite but not the data-source flip.
   - **Fix:** In the rewrite effect, seed the slug key before/after the `replaceState`: `queryClient.setQueryData(["product-by-slug", productSlug], byIdQuery.data)` (same DTO shape, per the page's own comment at `:123-125`; `useQueryClient` is already imported). ~2 lines. No decomposition pin touches this effect (`product-decomposition-r135` pins imports/handler ownership only).
   - **If we skip it:** Legacy-link visitors on slow Libyan mobile links watch the money page blink out and re-load once per visit, and the API serves each legacy PDP visit twice.

2. **PDP→PDP navigation (recommendations) keeps the previous product's validated coupon on the buy CTA** (`frontend/src/pages/product.tsx:246-250`, `:340`, `:794-799`)
   - **What this is:** The recommendations rail links are same-route wouter links (`components/product/RecommendationsSection.tsx:72-75`), so navigating to another product reuses the mounted `ProductPage` — component state survives.
   - **Problem:** The coupon-void effect is keyed ONLY on `[selectedVariant?.id]`. When both the old and the new product have no variants, `selectedVariant` is `null` in both renders, the dep never changes, and `couponResult` validated against product A's price survives onto product B: the buy CTA then shows A's `final_amount` (`:794`), and `handleBuyIntent` sends A's validated code with B's order (`:340`). The server re-validates against B's price, so the charge is server-correct — but the label the shopper approves is wrong (the exact R94-A1 #9 "confirmed X, charged Y" class), and a coupon invalid for B surfaces a confusing 400. The stale `error` message from a failed A purchase also persists into B.
   - **Fix:** Add the product identity to the void effect's deps — `}, [selectedVariant?.id, product?.id]);` — one line, strictly more voiding (the safe direction), keeps the "input preserved for one-tap re-validate" behavior.
   - **If we skip it:** A shopper cross-selling between two variant-less products with a coupon sees a wrong amount on the money CTA and can hit an unexplained rejection.

3. **The login↔register tab links drop `?ref=` — a referred signup loses its attribution** (`frontend/src/pages/login.tsx:174-189` and `:300-317`; `frontend/src/pages/register.tsx:105-112`)
   - **What this is:** All three auth surfaces read the referral code from the live URL at click time (`AuthProviders.tsx:129`, `TelegramLoginButton.tsx:77-79`, `WhatsAppPhoneSignIn.tsx:207-212`), and the register page reads it for the banner (`register.tsx:26-33`).
   - **Problem:** The tab links forward only `?redirect=`. A visitor landing on `/register?ref=CODE` who taps «تسجيل الدخول» lands on `/login` (ref gone). Signing up from THERE via WhatsApp (the backend handles new + returning users identically) already loses the referral; toggling back to «حساب جديد» also lands without `ref`. The referrer's 50-point credit (≙ 0.50 د.ل) never lands — a concrete value loss on the dominant referral journey.
   - **Fix:** Thread `ref` through the three link builders exactly the way R123-E4a threaded `redirect`: login's register-tab link, login's footer register link, register's login-tab link (append `?/&ref=` when present). 3 small edits, mirrors an existing tested idiom.
   - **If we skip it:** Every referred visitor who switches tabs before signing up signs up unattributed; the referral program silently under-credits.

4. **Eight storefront routes never set a document title — the route announcer is silent between them** (`pages/wallet.tsx`, `pages/orders.tsx`, `pages/order-detail.tsx`, `pages/loyalty.tsx`, `pages/referrals.tsx`, `pages/profile.tsx`, `pages/login.tsx`, `pages/register.tsx` — none call `useSeo`; vs `app/routes.tsx:349-355` and `:399-407`)
   - **What this is:** F3-07's `RouteAnnouncer` announces each SPA navigation by reading `document.title`, and its docblock claims "Every route maintains its `<title>` via its useSeo / MetaTags block, so the announced text is the page's real name (e.g. «SubNation — المحفظة»)".
   - **Problem:** Those eight routes set no title, so the App fallback's generic «SubNation — سوق الاشتراكات الرقمية» owns the head on all of them. Navigating wallet → orders → loyalty → referrals → profile never changes the title, and the announcer deliberately skips same-title navigations (`routes.tsx:404`) — a screen-reader user gets NO cue that the page changed on the whole account surface (focus moves, but no utterance), and the browser tab shows the generic title on money pages. The admin console got exactly this fix in R125 (A6 B-1: per-route `document.title`, pinned by `admin-document-title.test.tsx`) and R140-h fixed status/notifications/not-found/terms — the storefront account family was skipped. No test pins these pages' titles (meta-quality-r140 only covers the robots directive for them, via the fallback).
   - **Fix:** One `useSeo({ title: "… — SubNation", …, robots: "noindex,follow" })` block per page (~6 lines × 8), matching notifications.tsx's shape; announcements and tab titles start working with zero announcer changes.
   - **If we skip it:** Arabic screen-reader users traverse the account/money surfaces with silent route changes — the exact gap F3-07 was built to close — and multi-tab sighted users can't tell wallet from orders by tab.

## Nice to have

5. **`visibleOrders` useMemo never memoizes** (`frontend/src/pages/orders.tsx:289-300`)
   - **What this is:** The pending/completed/failed buckets are plain `.filter()` calls in the render body (fresh array identities every render), and `visibleOrders`' useMemo lists them as deps.
   - **Problem:** The memo comparison fails on identity every render, so the memoized work re-runs on every keystroke-free re-render (load-more spinner flips, overlay updates). Not a wrong result — just wasted work the memo pretends to prevent.
   - **Fix:** Either wrap the three buckets in one `useMemo([orders])` (the admin/topups.tsx R125-I2 idiom, ~3 lines) or delete the `visibleOrders` memo. Either direction is smaller than the current shape.
   - **If we skip it:** A few redundant array passes per render on a ≤few-hundred-row list — invisible to users.

6. **`order-detail.tsx` carries a near-duplicate of the shared credential `CopyField`** (`frontend/src/pages/order-detail.tsx:44-103` vs `frontend/src/components/product/CopyField.tsx:10-65`)
   - **What this is:** Both render the paid-credential row: label, LTR `select-text` value, `•`-mask + 44px reveal toggle for secrets, shared `CopyButton`. Same props, same logic, same rationale comments (the component's own docblock even says it was "ported from order-detail's CopyField (V2-H10)").
   - **Problem:** Two copies of the one component that displays paid passwords must now change together (a masking or a11y fix on one silently misses the other) — the classic near-copy that R135's extraction left behind on the page side. Only real diff: row padding/hover classes.
   - **Fix:** Import the shared `CopyField` in order-detail and add an optional row `className` prop to it (keeps byte-identical output); delete the page-local copy. ~-55 lines. Decomposition pins don't cover order-detail's internals (only render suites — `order-refund-receipt`, `order-decrypt-failed` — which the identical-DOM swap keeps green; run them with the change).
   - **If we skip it:** ~60 duplicated lines to read and keep in sync on the receipt surface of the money path.
