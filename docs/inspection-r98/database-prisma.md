> **Agent:** R98-A2 (diagnostic only — zero source modifications, zero DB writes, no prisma/drizzle commands run).
> **Scope:** schema↔migrations parity · index coverage vs query patterns · N+1 · transaction boundaries · connection lifecycle · money/decimal handling · integrity constraints · raw SQL.

## 1. Findings

### [P2] R98-DB-01 — V1-M16 variant indexes are live-only: boot SQL creates them, schema TS + drizzle chain + snapshot don't
- **file:line:** `backend/src/migrate.ts:729` and `backend/src/migrate.ts:746` vs `shared/db/src/schema/orders.ts:83-92`, `shared/db/src/schema/inventory.ts:57-61`, `shared/db/drizzle/*.sql` (0 matches), `shared/db/drizzle/meta/0010_snapshot.json` (0 matches — verified programmatically).
- **Evidence:** `applyProductVariantsStage` creates `idx_orders_variant ON orders(variant_id)` and `idx_inventory_variant ON inventory(variant_id)`; `orders.ts` declares 6 indexes (user/product/status/created/status_created/user_created) and `inventory.ts` 3 (product/sold/product_sold) — neither declares the variant index. `rg idx_orders_variant|idx_inventory_variant shared/db/drizzle/` → no hits; snapshot index lists for `orders`/`inventory` (printed via python) confirm absence.
- **Why:** This re-opens the exact "live-only index, drizzle push drops it" class round-97 just closed (D6/D7/D8) — V1-M16 (2026-09-20) post-dates that round. Consumers of the dropped indexes: `DELETE /api/admin/products/:id/variants/:variantId` order-history guard (`routes/admin/product-variants.ts:334-337`, `COUNT(orders WHERE variant_id = X)` → seq scan) and checkout's variant-scoped inventory claim (`services/checkout.service.ts:399-411` — served today by the `(product_id, is_sold)` prefix, so checkout degrades gracefully but parity discipline is broken and introspection lies).
- **Minimal fix:** declare both in schema TS (`orders.ts`: `index("idx_orders_variant").on(t.variantId)`; `inventory.ts`: same on `t.variantId`), regenerate migration 0011, or at minimum add the mirror-comment idiom used by `products.ts:106-113`.

### [P2] R98-DB-02 — R97 fix item #4 executed only half its mirror list: `idx_forecasts_at_risk_runout` + `fk_cart_items_user` still live-only
- **file:line:** `backend/src/migrate.ts:2168-2170` (partial index) and `backend/src/migrate.ts:1141-1143` (cart FKs) vs `shared/db/src/schema/inventory_forecasts.ts:67-71` (3 indexes only), `shared/db/src/schema/cart.ts:24` (`userId: integer("user_id").notNull()` — no `.references()`), snapshot (`cart_items` FKs: product + variant only; `at_risk_runout`: 0 mentions).
- **Evidence:** R97's own priority table row #4 (P2) lists four mirrors: `uniq_wallet_topups_payment_reference`, `idx_users_phone_trgm`, `idx_forecasts_at_risk_runout`, `FKs cart_items`. Wave 97-F7 item 3 executed only the first two; the forecast partial index and the `user_id` FK were never mirrored. The product FK was mirrored (`cart.ts:25-35`) — only `fk_cart_items_user` is missing.
- **Why:** same push-drop class: a `drizzle-kit push` drops the forecast panel's hot-path partial index (`WHERE at_risk = true` — the exact pattern the admin risk panel filters) and drops the cart→user cascade FK (user deletion then leaves orphan cart rows instead of cascading).
- **Minimal fix:** add to `inventory_forecasts.ts`: `index("idx_forecasts_at_risk_runout").on(t.atRisk, t.predictedRunoutAt).where(sql`at_risk = true`)`; add `.references(() => usersTable.id, { onDelete: "cascade" })` to `cart.ts` `userId`; regenerate.

### [P2] R98-DB-03 — forecast/enrichment CHECK constraints exist only in boot SQL and in NO test harness
- **file:line:** `backend/src/migrate.ts:2160-2163` (`chk_forecast_confidence`, `chk_forecast_insufficient_consistency`) and `backend/src/migrate.ts:2228-2235` (`chk_enrichment_state`, `chk_enrichment_field`, `chk_enrichment_published_consistency`, `chk_enrichment_rejected_consistency`) vs `shared/db/src/schema/inventory_forecasts.ts` (no `check()`), `shared/db/src/schema/enrichment_drafts.ts` (no `check()`), `backend/src/test/db.ts:46-316` (17-table pglite harness — neither table present), 0010 snapshot (checks: `[]` for both tables — verified).
- **Evidence:** grep across backend shows the constraint names only in migrate.ts. Unlike the V1-M9 money CHECKs (consciously boot-owned but pinned verbatim in the pglite harness by `schema-parity.test.ts`), these six have no owner in TS and no test coverage anywhere.
- **Why:** (a) a `drizzle-kit push` silently drops all six — the enrichment draft state machine (`drafted|published|rejected|draft_invalid` + published_at/rejected_at consistency) and forecast nullable-metric consistency lose their last line of defense; (b) the test blind spot is the exact A10 class round-93 fixed for money constraints: tests can certify writes production would reject (and vice versa).
- **Minimal fix:** declare via drizzle `check()` in both schema files (idiom already proven in `scheduler-leader-lease.ts:36-40`), regenerate, and add the two tables + CHECKs to the pglite DDL when their service tests need them.

### [P3] R98-DB-04 — `auth_activity.created_at` type drift: TS `timestamp` vs live/boot `timestamptz`
- **file:line:** `shared/db/src/schema/auth_activity.ts:24` (`timestamp("created_at")` — no `withTimezone`) vs `backend/src/migrate.ts:1301` (`created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`) vs `shared/db/drizzle/0000_nifty_green_goblin.sql:58` (`timestamp DEFAULT now()`).
- **Evidence:** only table in the schema whose `created_at` lacks `withTimezone:true` (all 36 other tables have it).
- **Why:** `drizzle-kit generate` stays a no-op only because the snapshot shares the TS type; a push would `ALTER COLUMN … TYPE timestamp` on the live timestamptz column (no value shift while session TZ=UTC, but it breaks the parity discipline R97 established and confuses any future introspect/generate cycle).
- **Minimal fix:** `timestamp("created_at", { withTimezone: true })` + regenerate 0011.

### [P3] R98-DB-05 — `uniq_product_variants_plan_duration` cannot dedup NULL axes; the schema docstring promises an `''`-normalization the code doesn't do
- **file:line:** `shared/db/src/schema/product-variants.ts:86-93` (docstring "API layer normalizes absent axes to empty strings") vs `backend/src/routes/admin/product-variants.ts:81-91` (`normalizeLabels` returns **null** for empty strings), `:157-167` / `:242-253` (dupe probes run OUTSIDE any transaction, `IS NOT DISTINCT FROM`).
- **Evidence:** PG btree UNIQUE treats NULLs as distinct, so two rows `(product_id, 'Family', NULL)` can coexist despite the unique index; the app probe (`IS NOT DISTINCT FROM`) is the only guard and it's a pre-insert TOCTOU — two concurrent POSTs both pass and both insert.
- **Why:** duplicate catalog options (admin double-click / concurrent creates) when either axis is absent; the docstring's stated mitigation doesn't exist, so the invariant the comment claims is false. Admin-only, price resolution unaffected ("cheapest-first") — hence P3, not P2.
- **Minimal fix:** `.nullsNotDistinct()` on the unique index (PG15+; Neon is 17) or make `normalizeLabels` return `""` as the docstring says (then the index dedups honestly).

### [P3] R98-DB-06 — `resolveProduct` runs one similarity query per candidate, sequentially, contradicting its own "single SQL query" doc
- **file:line:** `backend/src/services/copilot/admin-direct.ts:242-247` (doc: "run a single SQL query … and unions the results") vs `:261-287` (`for (const cand of candidates) { await db.execute(sql`…`) }`).
- **Evidence:** each candidate costs one round trip; typical candidate count after synonym/transliteration expansion is 3–8.
- **Why:** admin-copilot-only, trigram-indexed (`idx_products_name_trgm`), 56-product table → impact is latency, not load. But the comment-code mismatch will mislead the next auditor into thinking it's already batched.
- **Minimal fix:** one query with `UNION ALL` over candidate arms, or `Promise.all(candidates.map(...))`; fix the comment either way.

### [P3] R98-DB-07 — env.example tells the operator to use the DIRECT Neon URL; production actually runs the -pooler endpoint
- **file:line:** `config/env.example:17-19` ("Use the **direct** Neon URL (not the -pooler one)") vs `docs/NEON_MCP_SETUP.md:77`, `PLATFORM.md:9`, R97 live evidence (`ep-spring-term-avwgxrte-pooler.c-11…`).
- **Evidence:** live connection is the pooler endpoint while the checked-in guidance says the opposite.
- **Why:** contradictory operator guidance. The code itself handles both (SSL detection by hostname, channel_binding passthrough, `statement_timeout` via the pg startup packet — live boots through the pooler prove Neon's pgbouncer currently accepts it). Residual risk worth documenting: if a future URL/pooler change rejects the startup param, **every boot fails** with "unsupported startup parameter: statement_timeout"; the safe fallback is setting it in a pool `connect` hook (`SET statement_timeout`) instead. Also: `pgbouncer=true` URL flag from the brief is a Prisma-only concept — nothing to configure for drizzle/pg.
- **Minimal fix:** align env.example with reality + add the fallback note to `shared/db/src/index.ts`'s R4 comment.

### [P3] R98-DB-08 — doc/lifecycle nits in the DB layer
- **file:line & evidence:**
  - `shared/db/src/index.ts:24-33` — comment says prod default 15 "matches render.yaml"; render.yaml:27-32 now pins **8** (2026-09-20 cold-start storm tuning). Stale doc.
  - `shared/db/src/index.ts:102-104` — `pool.on("error")` logs via `console.error` (not pino) and is NOT counted in `neonPoolErrorsTotal` (that counter is only fed by the query wrapper in `db-instrumentation.ts:234`) — idle-client errors (the Neon-suspend wake class) bypass the metric.

- **Why:** each is cosmetic, but this layer's reliability has been built on its comments being true.
- **Minimal fix:** 4 one-liners.

## 2. Scope verdicts (verified clean unless listed above)

**§1 schema↔migrations parity (fresh deploy).** `migrate.ts` creates all **40** tables the schema declares (verified 1:1 against the 0010 snapshot table set) and every column (products slug/seo/features/faq/description_long/cost_price, orders variant_id/variant_label, inventory variant_id/updated_at, cart variant columns, users organization_id, admin_users permissions/updated_at — all present in boot SQL). Fresh-deploy drift: **none**. Reverse drift (live-only objects) = findings 01–03. The drizzle TS↔snapshot↔SQL chain is internally consistent (snapshot re-emitted in 5b98bd3), so `drizzle-kit generate` is a no-op today.

**§2 index coverage vs query patterns.** Every hot filter/sort is covered: orders `user_id+created_at DESC` (`idx_orders_user_created`), `status+created_at` (`idx_orders_status_created`), `order_code` (UNIQUE); product_variants `product_id[+is_active]` (+ `priceLyd` sort in-memory, ≤500 rows); idempotency keys (PK + `idx_idempotency_keys_order`); coupons by `code` (UNIQUE backing index); sessions by PK / `idx_sessions_user_id`; wallet_ledger `(user_id, created_at)`; wallet_topups `payment_reference+status='approved'` served by the partial UNIQUE, `(status, created_at)`, `user_id`; whatsapp_otps `(phone, purpose, created_at)` + `expires_at`; login_attempts UNIQUE identifier (lockout race-proof); auth_activity 4 indexes; audit_logs 4; risk_events incl. keyset `(created_at DESC, id DESC)`; notifications `(user_id, is_read)`; ticket_replies `(ticket_id, created_at)` (V1-M15); admin_alerts dedupe `(dedupe_key, created_at)`; users email/created/referral_code/referred_by + phone trigram GIN; products 4 btree + slug UNIQUE + name trigram GIN. Known-and-queued (R97 P3 queue, not re-reported): admin `LOWER(order_code) LIKE '%q%'` seq scan. "Delivery log" has no table in this DB (owned by the external openwa gateway).

**§3 N+1.** Hot paths are batched: catalog = products join + 1 `inArray` variants query + flash-sale lookup (3 round trips, 30s+7d cached); orders/wallet lists are leftJoin; admin lists use `inArray` + Map (users.ts:48-59, products.ts:70-105, tickets.ts:77-110, support.ts:50-73). `Promise.all(variants.map(formatVariant))` (product-variants.ts:113) is NOT an N+1 — `getPricingConfig()` is 60s-cached with in-flight dedup (pricing-config.ts:102-141). Sequential awaited loops exist only in: bounded ctid-batch retention DELETEs (deliberate, lock-footprint rationale), the forecast cron's per-product upsert (~45 writes, offline), the copilot resolveProduct loop (finding 06), and the pricing-config bulk recompute loop (admin, bounded). Money paths: zero N+1.

**§4 transactions.** All 10 `db.transaction` sites verified: checkout (inventory `FOR UPDATE SKIP LOCKED` → CAS on wallet/points/lifetimeSpend → guarded coupon increment → order → ledger → in-tx idempotency claim; freshness re-checks for product/variant/flash-sale inside the tx), topup approve + createApprovedTopup (`pg_advisory_xact_lock` + in-tx duplicate check + guarded status flip + CAS credit + ledger + guarded referral flip), refund (in-tx re-reads, status-guarded flip AFTER credit so rollback covers both, credential revocation in-tx), adjustment (in-tx read + CAS + signed ledger), loyalty conversion (in-tx read + 3-column CAS + ledger), wallet submission (advisory lock + count-then-insert in one tx). Read-then-write races: none found on money paths — every pre-tx read is either re-read in-tx or protected by a value-based CAS predicate (`eq(numericCol, String(parseFloat(...)))` — value-based numeric equality, documented). Rollback paths: side effects (Telegram/alerts/notifications) deliberately deferred to post-commit (couponMaxedSignal object pattern). No nested transactions; `tx` passed via `DbOrTx` cast — correct.

**§5 connection lifecycle.** Pool (`shared/db/src/index.ts`): `max=DB_POOL_MAX` (render.yaml: 8), `idleTimeoutMillis=10s` (≪ Neon's ~5min suspend — connections close before the compute sleeps), `connectionTimeoutMillis=30s` (pool acquire; tuned for cold-start TLS/SNI wake), **`statement_timeout=15s` server-side per pooled connection** (R4), TCP keepalives 30s, SSL `rejectUnauthorized:true` + channel-binding support. Shutdown: `pool.end()` in the SIGTERM/SIGINT drain of BOTH `server.ts:245` and `worker.ts:148` (with force-exit timers). Neon wake/failover: boot classifies `25006/08006/08003/08001/57P01/57P03/ECONNRESET` as transient with retry (boot-migrations.ts:122-131) and re-throws critical errors (P0-4 discipline). Runtime mid-query failures surface through the query error path + slow-query histogram + `neonPoolErrorsTotal` (db-instrumentation.ts). "P1001/P1002" are Prisma codes — the pg equivalents here are handled. Residuals: finding 07/08.

**§6 money/decimal.** All money columns are `numeric(10,2)` (users.walletBalance, lifetime_spend, orders.amount/discount_amount/wallet_balance_before/after, wallet_topups.amount, wallet_ledger.amount/balance_before/after, coupons.value/min_order_amount, product_variants.price_lyd/cost_price, products.price/cost_price). JS conversion policy centralized in `toNumber` (null/""/NaN/Infinity → fallback, never propagates — numeric.ts) and every write is `toFixed(2)`/`round2`-rounded then stringified; aggregate sums (`SUM(amount)`) are computed by Postgres on numeric — no JS float accumulation. Drizzle numeric returns strings everywhere (no silent float mapping). The ×20 rule = `computeRetailLYD(cost, {usdToLyd:10, markupPercent:100})` (pricing-config.ts:68) — **enforced at write time** on admin variant create (POST derives from cost), PATCH (recomputes when cost changes), the bulk recompute endpoint, and the import script; an explicit `price_lyd` override (0.01–1,000,000 bounds) is allowed, flagged `priceOverride` in the audit log (product-variants.ts:150-153, 202) — a documented, audited convention, not a strict invariant. LYD display: 2-decimal + "د.ل" consistently; loyalty points = `Math.floor(finalPrice)` (integer, no float money).

**§7 integrity constraints.** Unique: order_code, users phone/google/telegram/firebase_uid/referral_code, coupons code, referral referee_id, cart (user_id, product_id), product_variants (product_id, plan, duration — NULL caveat = finding 05), flash_sales active singleton, login_attempts identifier, topups approved payment_reference (partial), forecast (product_id, forecast_date), user_auth_identities (provider, provider_uid). onDelete: correct per table (orders.product restrict; orders/inventory variant set-null + immutable variant_label copy; orders.user/inventory.product/ledger/topups/tickets/notifications cascade; risk_events user set-null; copilot previews admin restrict). Money CHECKs: `wallet_balance >= 0`, `topups amount > 0`, `ledger amount <> 0`, `coupons used_count <= max_uses` — live (V1-M9/V1-M10) and pinned in the pglite harness by `schema-parity.test.ts` (consciously boot-owned — not re-reported). Gaps = findings 01–03 + 05. Nullable-field sanity: good (variant columns nullable with documented legacy semantics; discount_amount NOT NULL aligned R97-DB-03).

**§8 raw SQL.** All `db.execute(sql\`…\`)` interpolate JS values as **bound parameters** (drizzle `sql` template semantics) — verified in stats.ts, referrals.ts, risk.ts, forecast-retention.ts, admin-direct.ts, account-link-consent.ts, pg-leader-lease.ts, session-liveness/admin-session CAS. `sql.raw(` appears only with constant fragments: retention predicates (`p.expires_at < NOW() - INTERVAL '24 hours'`), DDL assembled from constant arrays (migrate.ts fkStatements/USERS_*_DDL — table+column names only), and the test TRUNCATE list. **Zero user input reaches `sql.raw` or string concatenation.** No `$queryRawUnsafe` equivalent exists in this codebase. Type mapping: `db.execute` results handled with the `rows ?? array` dual shape (node-pg vs pglite) consistently.
